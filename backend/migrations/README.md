# Database Migrations

This directory contains Alembic database migrations for the Sentinel backend.

## Overview

Alembic manages database schema changes through versioned migration scripts. Each migration represents a single atomic change to the database schema (e.g., creating a table, adding a column, creating an index).

**Traces to:**
- 07-Backend-Development-Standards §8 (migration standards)
- 22-Engineering-Backlog E3.T2 (Alembic infrastructure)

## Configuration

### Environment Variables

Migrations require `DATABASE_MIGRATION_URL` to be set in the environment:

```bash
export DATABASE_MIGRATION_URL="postgresql://user:password@localhost:5432/dbname"
```

**Security note:** `DATABASE_MIGRATION_URL` should use credentials with DDL privileges (CREATE TABLE, ALTER TABLE, DROP TABLE) while `DATABASE_URL` (used by the application) should have restricted privileges (SELECT, INSERT, UPDATE, DELETE only).

**Traces to:** 08-Security-Architecture §9 (least privilege, separate migration credentials)

### Connection String Format

- **Migrations (sync):** `postgresql://user:pass@host:port/db`
- **Application (async):** `postgresql+asyncpg://user:pass@host:port/db`

Alembic uses the sync `psycopg2` driver for migrations. The `env.py` automatically converts `postgresql+asyncpg://` URLs to `postgresql://` for migration operations.

## Common Commands

### Create a New Migration (Autogenerate)

Autogenerate detects changes to ORM models and creates migration scripts:

```bash
cd backend
python -m alembic revision --autogenerate -m "descriptive_message"
```

**Example:**
```bash
python -m alembic revision --autogenerate -m "add_user_table"
```

**Important:** Always review autogenerated migrations before applying. Alembic may miss:
- Renamed columns (appears as drop + add)
- Data migrations
- Complex constraint changes
- Index optimizations

### Create an Empty Migration (Manual)

For data migrations or complex schema changes:

```bash
python -m alembic revision -m "descriptive_message"
```

### Apply Migrations (Upgrade)

Apply all pending migrations to the database:

```bash
python -m alembic upgrade head
```

Apply migrations up to a specific revision:

```bash
python -m alembic upgrade <revision_id>
```

### Rollback Migrations (Downgrade)

Rollback to a specific revision:

```bash
python -m alembic downgrade <revision_id>
```

Rollback all migrations:

```bash
python -m alembic downgrade base
```

### Check Current Revision

Show the current database revision:

```bash
python -m alembic current
```

### Show Migration History

Display all migrations:

```bash
python -m alembic history
```

Show verbose history with details:

```bash
python -m alembic history --verbose
```

## Migration Naming Convention

Migration files follow this pattern:

```
YYYYMMDD_HHMM_<revision_id>_<message>.py
```

**Example:**
```
20260717_2112_a1b2c3d4e5f6_add_user_table.py
```

This ensures chronological ordering in the filesystem.

## Writing Migrations

### Basic Structure

```python
"""descriptive message

Revision ID: a1b2c3d4e5f6
Revises: previous_revision_id
Create Date: 2026-07-17 21:12:13.749213
"""

from collections.abc import Sequence

from alembic import op
import sqlalchemy as sa


# revision identifiers, used by Alembic.
revision: str = "a1b2c3d4e5f6"
down_revision: str | Sequence[str] | None = "previous_revision_id"
branch_labels: str | Sequence[str] | None = None
depends_on: str | Sequence[str] | None = None


def upgrade() -> None:
    """Upgrade schema."""
    # Forward migration logic
    op.create_table(
        "users",
        sa.Column("id", sa.UUID(), nullable=False),
        sa.Column("email", sa.String(), nullable=False),
        sa.PrimaryKeyConstraint("id", name="pk_users"),
    )


def downgrade() -> None:
    """Downgrade schema."""
    # Reverse migration logic
    op.drop_table("users")
```

### Best Practices

1. **Atomic Changes:** Each migration should represent a single logical change
2. **Reversible:** Always implement both `upgrade()` and `downgrade()`
3. **Idempotent:** Migrations should be safe to run multiple times
4. **Data Safety:** Use `batch_alter_table()` for complex changes on large tables
5. **Review Generated Code:** Always review autogenerated migrations before committing
6. **Test Rollback:** Test both upgrade and downgrade paths in development

**Traces to:** 07-Backend-Development-Standards §8 (migration quality standards)

### Common Operations

#### Create Table

```python
op.create_table(
    "table_name",
    sa.Column("id", sa.UUID(), nullable=False),
    sa.Column("created_at", sa.TIMESTAMP(timezone=True), nullable=False),
    sa.PrimaryKeyConstraint("id", name="pk_table_name"),
)
```

#### Add Column

```python
op.add_column("table_name", sa.Column("new_column", sa.String(), nullable=True))
```

#### Drop Column

```python
op.drop_column("table_name", "column_name")
```

#### Add Index

```python
op.create_index("ix_table_name_column", "table_name", ["column_name"])
```

#### Add Foreign Key

```python
op.create_foreign_key(
    "fk_table_name_other_id_other_table",
    "table_name",
    "other_table",
    ["other_id"],
    ["id"],
)
```

#### Execute Raw SQL

```python
op.execute(
    sa.text("""
    CREATE INDEX CONCURRENTLY ix_table_name_column
    ON table_name (column_name);
""")
)
```

## ORM Model Integration

Alembic autogenerate works by comparing `Base.metadata` (ORM models) to the current database schema.

**Critical:** All ORM models must be imported in `env.py` for autogenerate to detect them:

```python
# In migrations/env.py
from app.infrastructure.database.base import Base
from app.models.user import User  # Import all models
from app.models.upload import Upload

target_metadata = Base.metadata
```

If a model is not imported, its table will not appear in autogenerated migrations.

## Troubleshooting

### "Target database is not up to date"

Your database is behind the latest migration. Run:

```bash
python -m alembic upgrade head
```

### "Can't locate revision identified by 'xyz'"

The revision doesn't exist in your `migrations/versions/` directory. Ensure all team members have the latest migrations from version control.

### "No such table: alembic_version"

Alembic hasn't been initialized. Run:

```bash
python -m alembic upgrade head
```

This creates the `alembic_version` table and applies all migrations.

### Autogenerate Doesn't Detect Changes

1. Ensure your model is imported in `env.py`
2. Verify `Base.metadata` includes your model
3. Check that the model inherits from `BaseModel` or `Base`

## Production Deployment

### Pre-deployment Checklist

- [ ] All migrations tested in development
- [ ] Rollback (`downgrade`) tested for each migration
- [ ] Migrations reviewed for:
  - Locking behavior (ALTER TABLE locks entire table)
  - Performance impact on large tables
  - Data loss risks
- [ ] Backup created before deployment
- [ ] Migration execution time estimated (< 5 minutes preferred)

### Zero-Downtime Migrations

For production deployments with zero downtime:

1. **Additive changes first:** Add new columns/tables without removing old ones
2. **Deploy application:** Release code that works with both old and new schema
3. **Migrate data:** Backfill new columns if needed
4. **Remove old schema:** Drop old columns/tables in a later migration

**Traces to:** 07-Backend-Development-Standards §8 (zero-downtime migration strategy)

### Long-Running Migrations

For migrations that take > 5 minutes on production data:

1. Use `CONCURRENTLY` for index creation (doesn't lock table):
   ```python
   op.create_index("ix_name", "table", ["column"], postgresql_concurrently=True)
   ```

2. Use `batch_alter_table()` for multiple changes to the same table

3. Consider breaking into multiple migrations if changes are independent
