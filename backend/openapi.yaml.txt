(The literal wire-format details of 05-API-Specification.md
were not pasted verbatim into this session. This file is
therefore derived from the authoritative narrative context
supplied — PRD, Domain Model, Architecture, Database Design,
and API Specification summary — and encodes the following
explicit design decisions as binding contract rules rather
than invented behavior):
1. Digital Asset identity is the SHA-256 hash of its content,
NEVER the filename. Two Uploads with the same hash resolve
to the SAME DigitalAsset (deduplication).
2. DigitalAsset is immutable. There is no update endpoint.
If content changes, a new DigitalAsset (new hash) is created.
3. Analysis records are append-only and versioned. Re-running
an analyzer against the same asset creates Analysis vN+1;
it never overwrites vN. There is no update endpoint for
Analysis.
4. The platform never emits a bare "safe" verdict. Every
Analysis/Report carries verdict + evidence + confidence +
recommendation ("explainability first").
5. Uploads are processed through an async pipeline (validate →
hash → duplicate-check → store → extract metadata → queue).
Analyses are triggered explicitly against a DigitalAsset by
selecting one or more Analyzers, and are executed
asynchronously by workers (queue/worker pattern). Workers
never talk to browsers directly; clients poll or fetch
results via REST.
6. Files are stored in S3-compatible object storage; PostgreSQL
stores metadata only. This has no direct bearing on the
wire contract but explains why Upload/DigitalAsset expose
a storageRef/download-style relationship rather than
embedding binary content in JSON responses.
7. Roles: admin, analyst, viewer (assumed from PRD personas).
8. Max upload size assumed at 100 MB; allow-listed MIME types
assumed (pdf, common image types, zip, common docs).
9. Idempotency-Key is honored on POST /uploads and POST
/analyses so retried client requests do not create
duplicate Upload/Analysis records.
10. Rate limiting returns 429 with a Retry-After header.

info:
title: Sentinel API
description: |
Sentinel is an AI-native Digital Asset Intelligence Platform.

text

Rather than answering "is this malware?" the way legacy antivirus tools do,
Sentinel answers a broader set of trust questions for any digital asset a
user encounters — files, images, emails, URLs, QR codes, archives:

- Can I trust this?
- Is this phishing?
- Is this fake?
- Is this suspicious?
- What evidence supports that conclusion?
- What should I do?

## Platform-first pipeline
Every asset type flows through the same generic pipeline:

`Upload → Validate → Hash → Duplicate Detection → Object Storage →
Metadata → Queue → Worker → Analyzer → Analysis → Report → History`

Only the **Analyzer** varies by asset type or intelligence need
(Security Analyzer, OCR Analyzer, Metadata Analyzer, AI Document
Analyzer, Image Analyzer, and future custom analyzers).

## Core invariants enforced by this API
- **Immutable assets**: a `DigitalAsset`'s identity is its SHA-256 hash,
  never its filename. Re-uploading identical content resolves to the
  same asset.
- **Versioned analyses**: analyses are append-only. Re-analyzing an
  asset creates a new `Analysis` version; prior versions are preserved.
- **Explainability**: no endpoint ever returns a bare "safe" verdict —
  every analysis result includes evidence, confidence, and a
  recommendation.
- **Asynchronous processing**: uploads and analyses are queued and
  processed by workers; clients poll for status or retrieve completed
  results.

## Authentication
JWT access/refresh tokens. Obtain a pair via `POST /auth/login`,
authenticate with `Authorization: Bearer <accessToken>`, and renew via
`POST /auth/refresh` using `Authorization: Bearer <refreshToken>`.

## Idempotency
`POST /uploads` and `POST /analyses` accept an `Idempotency-Key` header
so that safe client retries do not create duplicate resources.

## Errors
All errors share a single envelope (see `Error` schema) and carry a
`requestId` for correlation with server-side logs.
